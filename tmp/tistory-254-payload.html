에셋번들 패치의 핵심은 번들을 어떻게 만드느냐가 아니라, 클라이언트가 무엇이 바뀌었는지 판단하는 기준을 어디에 두느냐다. 기준을 파일 목록과 해시로 고정하면 사운드 하나만 고쳐도 앱 전체 리소스를 다시 받는 일이 사라진다.

몇 년 전 개인 프로젝트에서 이 구조를 직접 만들어 굴렸다. 지금은 Addressables가 같은 일을 상당 부분 대신해 주지만, 손으로 만들어 보면 자동화된 도구가 실제로 무엇을 판정하고 있는지가 보인다. 그 판정 기준과, 당시 실제로 걸렸던 캐시 함정까지 정리한다.

왜 전체를 다시 받게 되는가

기준이 "버전이 올라갔다"뿐이면 클라이언트는 개별 파일의 변경 여부를 알 방법이 없다. 그래서 버전이 하나라도 오르면 그 버전 폴더의 리소스를 통째로 내려받는다.

이게 실제로 아픈 이유는 대역폭보다 이탈이다. 게임을 켰는데 진행 바가 몇십 메가부터 시작하면 그 자리에서 앱을 닫는 사용자가 생긴다. 리소스 한 개를 고친 패치와 전면 교체 패치가 사용자 입장에서 구분되지 않는 게 문제다.

해시 리스트를 먼저 받게 한다

해결은 단순하다. 리소스 본체보다 먼저 받는 작은 메타 파일을 하나 두고, 거기에 파일명·해시·크기를 전부 적는다. 당시 info.json이라 부른 파일은 이런 모양이었다.

{
  "version": "0.0.1",
  "createtime": "2016-11-07T08:49:45.272Z",
  "files": [
    ["sound_bgm_town.sound", "fcf818d317c121f4f7593eb17a1430c9", 4203],
    ["sound_ui_click.sound", "0720ff22c1e2c2ca72bf3621899eddb7", 8418],
    ["atlas_character.atlas", "64a57c4e458e985ebedafcd656064f40", 355910]
  ]
}

이 파일은 빌드 후 스크립트가 manifest를 읽어 md5와 바이트 크기를 계산해 자동 생성했다. 사람이 손으로 적는 순간 빠뜨림이 생기기 때문에, 생성 단계를 빌드 파이프라인 안에 넣는 편이 안전하다.

클라이언트 동작은 세 단계다. 먼저 info.json만 받는다(수 KB). 로컬에 저장된 이전 목록과 파일 단위로 해시를 비교한다. 해시가 다르거나 목록에 없는 파일만 내려받는다.

여기서 중요한 건 판단 기준이 "시간"이나 "기억"이 아니라 해시라는 점이다. 파일 수정 시각이나 "이번 패치에 뭘 바꿨더라" 같은 사람의 기억에 기대면 반드시 틀린다. 해시는 내용이 같으면 같고 다르면 다르다.

경로를 버전/플랫폼/파일로 자르는 이유

배포 경로는 resources/버전/플랫폼/파일명 순서로 고정했다. 예를 들면 resources/0.0.1/android/Android.manifest 형태다.

버전을 플랫폼보다 위에 두면 롤백이 경로 교체 한 번으로 끝난다. 문제가 생겼을 때 클라이언트가 바라보는 기준 버전만 이전 값으로 되돌리면 되고, 이전 버전 폴더는 그대로 남아 있으므로 재빌드가 필요 없다.

기준 URL 자체는 서버가 접속 시점에 내려주는 설정값으로 받게 했다. CDN을 바꾸거나 특정 사용자군만 다른 경로로 보내야 할 때, 앱을 다시 심사받지 않고 서버 설정만 고치면 된다.

번들 이름이 같으면 캐시가 안 갈린다

당시 가장 오래 붙잡았던 문제다. 경로를 다르게 해서 올렸는데도 클라이언트가 예전 번들을 계속 쓰는 현상이 있었다.

이건 Unity 캐시의 알려진 동작이다. 공식 매뉴얼에 따르면 캐시된 AssetBundle은 URL의 마지막 세그먼트(파일명)와 버전으로만 식별되고, 도메인과 경로 정보는 캐시 판정에서 무시된다. 이름이 같은 서로 다른 번들을 다른 경로에서 받으면 캐시가 충돌한다. Unity 지원 문서에도 Cannot load cached AssetBundle. A file of the same name is already loaded from another AssetBundle 오류로 따로 정리돼 있다.

회피 방법은 캐시 식별용 이름을 직접 지정하는 것이다. UnityWebRequestAssetBundle.GetAssetBundle에 CachedAssetBundle 구조체를 넘기면 name 필드로 고유한 이름을 부여할 수 있고, 기본값인 "URL 마지막 세그먼트" 규칙에서 벗어난다.

참고로 당시 쓰던 WWW.LoadFromCacheOrDownload는 현재 공식 문서에 Obsolete로 표시돼 있다. 대체 API는 UnityWebRequestAssetBundle.GetAssetBundle이며, Hash128 또는 버전 인자를 받는 오버로드만 내장 캐시를 사용한다. 여기서 넘기는 해시는 어디까지나 식별자이고, Unity가 내려받은 콘텐츠를 해시로 검증해 주는 것은 아니라는 점도 문서에 명시돼 있다.

지금이라면 Addressables가 대신하는 것

Unity Addressables(현재 3.1)를 쓰면 위에서 손으로 만든 것 중 세 가지가 기본으로 딸려 온다.

첫째, 카탈로그 해시 비교다. 리모트 카탈로그로 빌드하면 런타임이 카탈로그 해시 파일을 비교해 캐시된 것보다 최신일 때만 내려받는다. Addressables.CheckForCatalogUpdates로 갱신 가능 여부만 조회하고, Addressables.UpdateCatalogs로 실제 적용하는 식으로 시점도 제어할 수 있다.

둘째, 변경분 판정과 번들 분리다. 콘텐츠 업데이트 빌드는 변경된 에셋만 새 파일명의 번들로 재생성하고 나머지는 기존 파일명을 유지한다. CDN에는 바뀐 것만 다시 올리면 된다. 직접 md5를 계산해 info.json을 만들던 단계가 통째로 사라지는 셈이다.

셋째, 런타임 갱신 흐름이다. 카탈로그 감지부터 다운로드, 메모리 반영까지가 API로 제공된다.

다만 자동이 곧 무결점은 아니다. Unity 문서 스스로 변경 판정에 쓰이는 AssetDatabase.GetAssetDependencyHash가 빌드 시점의 실제 번들 변경분을 정확히 반영하지 못할 수 있다고 경고한다. 결국 "무엇이 바뀌었다고 판정할 것인가"는 도구를 쓰든 직접 만들든 개발자가 이해하고 있어야 하는 부분으로 남는다.

새로 시작하는 프로젝트라면 직접 만들 이유는 거의 없다. Addressables로 시작하고, 배포처가 필요하면 Cloud Content Delivery 연동까지 공식 워크플로우가 준비돼 있다. 대신 패치가 반영되지 않는 상황을 만났을 때 어디를 열어봐야 하는지는 알아 둘 만하다. 카탈로그 해시가 갱신되지 않았는지, 번들 이름이 겹쳐 캐시가 안 갈리는지 — 둘 중 하나인 경우가 많다.

문서 링크는 발행 시점(2026년 7월) 기준이며, Unity 버전에 따라 번들되는 Addressables 버전과 API가 다를 수 있어 사용 중인 버전의 문서를 함께 확인하는 편이 좋다.
